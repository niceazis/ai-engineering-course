## 1. Barge-in이 해결하는 문제

Barge-in은 에이전트가 말하는 중 사용자가 실제로 발언권을 가져가려 할 때 에이전트의 음성 출력을 멈추고 사용자의 새 요청을 처리하는 기능입니다. 안내 음성이 끝날 때까지 고객에게 기다리라고 강제하는 것과 달리 대화 중 정정·질문이 가능해집니다.

정상 동작을 위해서는 **실제 사용자 음성 감지 → 중단 의도 판별 → 생성·재생 정지 → 새 발화 인식 → 대화 이력 보정**이 필요합니다.

## 2. 음성 에이전트 내부에서의 위치

```text
마이크 → AEC → VAD → STT → 중단 의도 판별
                             │
                       진짜 중단 판정
                             ↓
                    TTS/LLM 취소 신호
                        ├─ 재생 큐 비우기
                        ├─ 사용자 입력 저장
                        └─ 재생된 범위만 문맥에 보존
```

AEC(Acoustic Echo Cancellation)는 에이전트 자신의 목소리가 스피커에서 마이크로 돌아와 새로운 사용자 음성으로 오인되는 현상을 억제합니다. VAD는 음성 존재 여부를 감지할 뿐, 말한 사람이 누구인지나 사용자의 발언권 요청 의도를 보장하지 않습니다.

## 3. 문제 1: 에이전트가 자기 목소리를 듣는 경우

스피커폰에서 "오후 5시가 가능합니다"라는 TTS 음성이 마이크로 유입되면 VAD가 이를 발화로 인식할 수 있습니다. 그러면 에이전트가 스스로를 끊거나 STT가 자신의 문장을 사용자 요청으로 기록할 위험이 있습니다.

- 출력 음성 참조 신호를 사용하는 AEC를 켭니다.
- 잔여 에코·주변 TV·타인의 음성을 별도 테스트합니다.
- "음성이 감지됨"만으로 곧바로 TTS를 중단하는 정책을 피합니다.

## 4. 문제 2: 맞장구와 실제 중단의 차이

| 에이전트 재생 중 소리 | 흔한 의미 | 기대 동작 |
| --- | --- | --- |
| "네", "음", "맞아요" | Backchannel(맞장구) | 계속 재생 |
| 기침, 주변 소음 | 실제 요청이 아님 | 계속 재생 |
| "아니요, 화요일로요" | 정정 | 재생 중단 후 새 요청 처리 |
| "그만", "잠깐요" | 짧은 중단 명령 | 빠르게 중단 |

너무 민감하면 사소한 소음에 계속 멈추고, 너무 둔감하면 고객의 정정을 놓칩니다. 발화 지속 시간, 인식된 단어, 주변 음향, 현재 대화 흐름을 함께 판단해야 합니다. 고정 지속 시간 조건만 쓰면 "그만" 같은 짧은 명령을 놓칠 수 있습니다.

## 5. 중단 직후 처리 순서

1. 지금 재생 중인 응답의 ID를 확인합니다.
2. TTS 및 필요하다면 LLM 생성을 취소합니다.
3. 이미 만들어진 음성도 남아 있을 수 있으므로 **재생 대기 오디오 큐를 비웁니다**.
4. 중단을 유발한 첫 단어가 사라지지 않도록 입력 오디오를 보존합니다.
5. 사용자에게 실제 재생된 답변 부분만 대화 이력으로 유지합니다.
6. 새 사용자 발화가 끝났는지 판정한 뒤 LLM에 다시 요청합니다.

외부 결제·주문·예약 도구는 새 요청의 의도·인증·필요한 확인이 끝난 후에만 실행해야 합니다.

## 6. 생성된 문장과 사용자가 들은 문장은 다릅니다

LLM이 다섯 문장을 만들었더라도 재생 도중 사용자가 말을 끊어 두 문장만 들었다면, 대화 이력에 다섯 문장 전부를 남겨서는 안 됩니다. 그렇게 하면 에이전트가 사용자에게 설명하지 않은 조건을 이미 설명했다고 잘못 가정할 수 있습니다.

반면 네트워크에 전송된 음성이 반드시 재생 완료됐다는 뜻도 아닙니다. 가능한 경우 TTS 재생 위치 확인을 바탕으로 가장 타당한 이력 경계를 계산합니다. Twilio ConversationRelay는 중단 시 재생된 부분에 맞춰 이전 메시지를 줄이는 통합 패턴을 설명합니다.

## 7. 중단 응답 속도와 오류를 함께 평가하기

`중단 후 소리가 멈추는 지연 = 감지 지연 + 의도 판별 지연 + 취소 전파 지연 + 버퍼 정리 지연`

이는 성능을 분해한 **설계용 산식**이며 원문이나 실측 데이터의 인용이 아닙니다. 측정 지표는 진짜 중단 성공률, 소음으로 인한 거짓 중단률, 실제 중단에서 출력이 멈추기까지의 지연, 사용자 첫 단어 보존율, 실제 재생된 문맥과 대화 이력의 일치율입니다.

중단 처리를 매우 민감하게 바꾸면 누락이 줄 수 있지만 거짓 중단이 늘어납니다. 고객 유형과 사용 환경에 따라 함께 검증해야 합니다.

## 8. 턴테이킹(turn-taking)과의 관계

턴테이킹은 누가 언제 말할 차례인지를 결정하는 전체 문제입니다. Endpointing은 **사용자 발화가 끝났는가**를 판단하고, barge-in은 **에이전트가 말하는 중 사용자가 끼어들었는가**를 판단합니다.

턴 중심으로 교대하는 시스템도 바지인 감지를 위해 수신·재생 오디오를 동시에 유지할 수 있습니다. 대화 정책의 half-duplex와 네트워크 음성 스트림의 양방향성을 혼동하지 않아야 합니다.

## 9. 예시: 요금제 안내 중 정정

1. 에이전트가 요금제 여러 개를 순서대로 소개합니다.
2. 고객이 "네"라고 맞장구를 치면 그대로 설명합니다.
3. 고객이 "잠깐, 무제한 요금제만 설명해 주세요"라고 말합니다.
4. 진짜 중단을 감지해 TTS와 재생 버퍼를 정지합니다.
5. 고객이 실제로 들은 문장만 이력에 남깁니다.
6. 새 사용자 요청이 완결되면 검증된 요금제 정보로 답합니다.

## 10. 실습 검증

- AEC를 켜거나 끄고 자기 음성으로 인한 오탐을 측정합니다.
- "네", 기침, 배경 음악, "그만"을 재생 중 입력해 결과를 비교합니다.
- 중단 직후 음성 큐가 실제로 비워지는지 검사합니다.
- 사용자 발화 첫 음절이 STT에서 유실되지 않는지 확인합니다.
- 이전 응답을 취소한 뒤 늦게 도착한 옛 출력 패킷이 재생되지 않는지 확인합니다.
- 중단된 답변의 미재생 구간이 이후 에이전트 문맥에서 제거됐는지 점검합니다.
