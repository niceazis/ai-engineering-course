# LLM은 왜 환각하는가? — 토큰 수준에서 이해하는 상세 학습 노트

> 원문: https://outcomeschool.com/blog/why-do-llms-hallucinate-the-token-level-explanation  
> 원저자: Amit Shekhar / Outcome School · 원문 게시: 2026-10-14  
> 출처 검증: 공식 upstream README의 4.6 소개와, 검색 엔진이 제공한 **원문 페이지의 색인 본문**(개념·표·예제·코드·여섯 원인·여섯 대응)을 대조했습니다. **원문 URL의 직접 페이지 열람은 실패**했습니다. 따라서 전체 그림·FAQ·페이지의 모든 요소를 직접 검증한 완전 대조본이라고 주장하지 않습니다.  
> 문서 성격: 원문 설명 순서와 수치·예제를 유지하면서 독립적으로 다시 쓴 한국어 기술 학습 노트입니다. 모든 확률 수치는 원문에 실린 **설명용 가상 분포**이며 측정한 실제 모델의 logprob가 아닙니다.

## 1. 환각(Hallucination)은 무엇인가?

LLM 환각은 사실과 다른 정보, 존재하지 않는 내용 또는 근거 없는 정보를 **그럴듯하고 단정적인 문장**으로 생성하는 현상입니다. 의도를 가진 거짓말과 구별해야 합니다. 원문의 출발점은 잘 알려지지 않은 가상의 저자에 대해 묻는 상황입니다.

- 질문: `Meera Joshi는 몇 년에 태어났는가?`
- 전제: 예제 속 모델은 이 저자에 관한 신뢰할 근거를 갖고 있지 않습니다.
- 출력: `Meera Joshi was born in 1962.`
- 문제: 문장 자체는 자연스럽지만 `1962`라는 수치를 검증한 적이 없습니다.

왜 이런 출력이 가능한지 이해하려면 문장을 통째로 생성한다고 생각하지 말고 **다음 토큰 하나를 결정하는 과정**을 살펴봐야 합니다.

## 2. 토큰은 단어와 일치하지 않을 수 있다

토큰은 모델이 텍스트를 처리할 때 쓰는 단위로, 단어 전체·단어 일부·숫자 일부·앞의 공백을 포함한 문자열이 될 수 있습니다. 원문은 다음처럼 나뉘는 **설명용 분절**을 사용합니다.

```text
Meera Joshi was born in 1962
"Me" | "era" | " Joshi" | " was" | " born" | " in" | " 19" | "62"
```

실제 분절은 토크나이저에 따라 달라집니다. 원문은 이후 확률 예제를 간단히 하기 위해 `1962` 같은 연도 전체를 토큰 하나로 **간주**합니다. 아래 표의 연도는 실제 토크나이저가 항상 하나의 토큰으로 인식한다는 뜻이 아닙니다.

## 3. LLM의 다음 토큰 선택 루프

모델은 지금까지의 문맥을 바탕으로 가능한 다음 토큰 각각에 점수 또는 확률을 부여하고, 디코딩 정책에 따라 하나를 선택합니다.

| 입력 접두부: `The capital of France is` | 다음 토큰 확률(원문 예시) |
| --- | ---: |
| ` Paris` | 92% |
| ` a` | 3% |
| ` the` | 2% |
| ` located` | 1% |
| 다른 모든 토큰 | 2% |

1. 이미 생성된 텍스트와 사용자 입력을 읽습니다.
2. 다음 토큰 후보들의 확률 분포를 구합니다.
3. 샘플링 또는 최대 확률 선택 등의 규칙으로 하나를 고릅니다.
4. 선택한 토큰을 문맥에 붙입니다.
5. 완료 조건에 이를 때까지 반복합니다.

**원문의 핵심 주장:** 이 기본 생성 루프에는 외부 사실에 대조해 참·거짓을 검증하는 단계가 별도로 들어 있지 않습니다. 다만 **검증 도구를 호출하는 모델·검색 결합 시스템·추론 절차**는 추가적인 검증 단계를 설계할 수 있으므로, 모든 AI 애플리케이션이 검증 불가능하다는 의미는 아닙니다.

## 4. 쉬운 토큰과 사실 토큰

`Meera Joshi was born in 1962`에서 `was`, `born`, `in`은 주어진 문장 구조상 쉽게 이어질 수 있는 표현입니다. 반면 `1962`는 실제 출생 연도를 단정하는 **사실 토큰(fact token)** 역할을 합니다.

- **쉬운 토큰:** 문법, 흔한 구문, 관용적 연결에 필요한 토큰.
- **사실 토큰:** 연도, 이름, 수치, DOI, 사건, 주소처럼 참·거짓을 좌우하는 정보를 실은 부분.
- **중요한 구별:** 여기서 쉬운 토큰/사실 토큰은 저자의 **설명용 구분**입니다. 모델 어휘 사전에 별도 공식 토큰 유형으로 지정되는 분류가 아닙니다.

문법적으로 자연스러운 토큰이 대부분이어도 핵심 사실 한 개가 틀리면 **문장 전체가 부정확**해질 수 있습니다.

## 5. 아는 사실을 선택할 때: 날카로운 분포(Sharp Guess)

원문의 예시는 `Albert Einstein was born in the year`라는 접두부 다음에 올 연도를 다룹니다.

| 다음 토큰 | 원문 예시 확률 |
| --- | ---: |
| `1879` | **95%** |
| `1878` | 2% |
| `1880` | 1% |
| 그 밖의 모든 토큰 | 2% |

가장 높은 후보가 나머지를 크게 앞서는 것을 저자는 **날카로운 추측**이라고 부릅니다. 이렇게 확률 질량이 특정 후보에 몰리면 무작위 샘플링을 하더라도 해당 후보가 자주 선택됩니다. 원문은 자주 등장해 학습된 사실의 직관적 설명으로 사용합니다.

단, **높은 모델 확률 = 사실임이 증명됨**은 아닙니다. 확률 분포의 날카로움은 모델의 다음 토큰 선호를 나타내지, 외부 세계의 진실성을 직접 측정한 값이 아닙니다.

## 6. 모르는 사실을 선택할 때: 평평한 분포(Flat Guess)

같은 형식으로 `Meera Joshi was born in the year`가 주어졌을 때 원문은 연도 후보의 확률이 고르게 퍼지는 모습을 보여줍니다.

| 연도 후보 | 원문 예시 확률 |
| --- | ---: |
| `1962` | 14% |
| `1958` | 13% |
| `1971` | 13% |
| `1965` | 12% |
| `1960` | 12% |
| `1968` | 12% |
| `1955` | 12% |
| `1974` | 12% |

여덟 후보 확률의 합은 **100%**입니다. 최댓값이 14%밖에 되지 않으므로 어느 연도가 맞는지 이 분포만으로 판단하기 어렵습니다. 원문은 100명의 학생이 아인슈타인의 연도는 비슷하게 외치지만 처음 듣는 저자의 연도는 서로 다르게 답하는 상황에 비유합니다.

- **Sharp:** 일부 후보에 확률이 집중됩니다.
- **Flat:** 후보들이 서로 비슷한 확률을 가집니다.
- **핵심:** 분포가 평평해도 일반적인 생성 과정은 그중 하나를 출력할 수 있습니다.

이 또한 단일 토큰의 불확실성에 관한 직관입니다. 실제 사실성 검증은 토큰 분포 외에도 문맥·출처·검증 모델·도구를 함께 사용해야 합니다.

## 7. 파이썬으로 보는 샘플링

원문은 `random.choices`를 사용해 두 분포에서 토큰을 뽑는 간단한 실험을 제시합니다. 아래 코드는 그 아이디어를 재구성한 **설명용 예제**입니다.

```python
import random

sharp_guess = {
    "1879": 0.95, "1878": 0.02, "1880": 0.01, "other": 0.02
}
flat_guess = {
    "1962": 0.14, "1958": 0.13, "1971": 0.13, "1965": 0.12,
    "1960": 0.12, "1968": 0.12, "1955": 0.12, "1974": 0.12,
}

def pick_next_token(distribution):
    tokens = list(distribution)
    weights = list(distribution.values())
    return random.choices(tokens, weights=weights, k=1)[0]

print(pick_next_token(sharp_guess))
print(pick_next_token(flat_guess))
```

- `sharp_guess`에서는 `1879`가 **95%**이므로 대부분 동일하게 나옵니다.
- `flat_guess`에서는 `1962`, `1971`, `1955` 등 여러 결과가 나타납니다.
- 실행할 때마다 두 번째 출력은 달라질 수 있으며, 코드에는 **정답 검사**가 없습니다.
- 이는 **완전한 LLM 구현이 아닙니다.** 실제 모델은 토큰별 logit 계산, temperature·top-k/top-p 등 추가 디코딩 과정을 갖습니다.

## 8. 원인 1 — 모른다는 이유로 빈칸을 건너뛰는 별도 선택지는 없다

원문의 기본 생성 예제에서 연도를 출력해야 할 문맥이 만들어지면 모델은 허용된 토큰 가운데 하나를 선택합니다. 모델이 모르는 사실에 대해 `I do not know`를 말하려면, **그 표현이 다음 출력으로 선택될 가능성**이 충분히 높아야 합니다.

원문은 학습 자료와 평가 방식이 종종 단정적인 정답 형식의 출력을 선호해, 모르는 사실에서도 연도·이름·숫자가 출력될 수 있다고 설명합니다. 이는 실험용으로 **모든 빈칸에 답을 적어야 하는 시험**에 비유됩니다.

**엄밀한 보완:** EOS/종료 및 `모릅니다`라는 일반 토큰 시퀀스 자체는 존재할 수 있습니다. 저자의 'skip 옵션 없음'은 원문의 **단순화된 토큰 선택 상황**을 설명하는 표현으로 이해해야 합니다. 보류·거절 행동은 학습과 시스템 설계에 따라 가능합니다.

## 9. 원인 2 — 평평한 분포에서 샘플링의 무작위성이 오답을 고른다

원문은 동일한 질문을 다섯 번 했을 때 다음처럼 서로 다른 답을 받는 상황을 보여줍니다.

| 실행 | 답변의 출생 연도 |
| --- | --- |
| 1 | 1962 |
| 2 | 1971 |
| 3 | 1955 |
| 4 | 1962 |
| 5 | 1968 |

이 답들의 문체는 모두 단정적이지만 실제 근거가 없을 수 있습니다. Temperature를 낮추면 높은 확률 후보가 반복 선택되므로 출력이 안정적일 수는 있으나, **항상 1962를 말한다고 1962가 정답이 되는 것은 아닙니다.**

`temperature=0`을 이용한 greedy decoding도 근거 없는 최상위 후보를 반복할 수 있습니다. 출력 일관성과 사실 정확도는 별개의 측정 대상입니다.

## 10. 원인 3 — 출력한 토큰을 같은 순방향 생성에서 되돌릴 수 없다

원문의 질문은 `3,827은 소수인가?`입니다. 원문은 첫 응답 후보를 가상으로 **Yes 52% / No 48%**라고 설정합니다. 모델이 `Yes`를 먼저 선택했다고 가정해 봅시다.

실제로는 다음처럼 나누어떨어집니다.

```text
3,827 = 43 × 89
따라서 3,827은 합성수이며 "No"가 정답입니다.
```

순방향 autoregressive 생성은 방금 고른 `Yes`를 삭제하고 과거 토큰의 자리에 `No`를 끼워 넣는 방식이 아닙니다. 후속 토큰만 이어 붙입니다. **따라서 앞부분의 작은 선택이 전체 답의 방향을 고정**할 수 있습니다.

다만 응답을 새로 생성하거나 별도 편집·수정 단계를 두는 애플리케이션은 첫 생성 결과를 **사후 수정**할 수 있습니다. 원문의 설명은 한 번의 순방향 생성에 관한 것입니다.

## 11. 원인 4 — 틀린 토큰이 뒤따르는 설명의 전제가 된다

첫 토큰이 `Yes`라면 뒤따르는 토큰은 그 선택을 정당화하는 문장을 자연스럽게 이어 만들 수 있습니다.

- 잘못된 결론: `3,827은 소수다.`
- 뒤따르는 오류: `1과 자기 자신 외에는 나누어떨어지지 않기 때문이다.`
- 실제 사실: `43 × 89 = 3,827`로 반박됩니다.

출생 연도 예제에서도 `1962`라고 한번 생성한 뒤, `1970년대에 성장했고 1980년대 말에 첫 책을 출판했다`는 식의 허구적 세부사항이 확장될 수 있습니다. **각 다음 토큰은 앞서 나온 잘못된 문맥에도 조건화**되므로 하나의 오류가 그럴듯한 이야기로 증식합니다.

## 12. 원인 5 — 그럴듯한 조각들이 합쳐져 실재하지 않는 인용을 만든다

원문은 가상 논문 참고문헌을 설명합니다.

- 저자: `Sharma, A.`, `Patel, R.`
- 연도: `2019`
- 제목: `Using AI to Detect Crop Diseases`
- 학술지: `Journal of Agricultural AI`

각 부분은 해당 분야에서 언뜻 있을 법합니다. 그러나 **그 조합 전체가 실제 출판물임을 증명하지는 못합니다.** 원문은 정확히 이 가상 조합이 존재하지 않는다고 가정합니다. 그러므로 이 인용을 실재 논문으로 취급하거나 참고문헌에 그대로 넣어서는 안 됩니다.

DOI, 출판사 목록, 원문 문서 등 **외부 출처와의 대조**가 필요합니다.

## 13. 원인 6 — 최종 문자열에 내부 불확실성이 표시되지 않는다

- Einstein 예제에서 `1879`는 **95%**였습니다.
- 저자 예제에서 `1962`는 **14%**였습니다.

하지만 최종 출력에는 숫자 **1879** 또는 **1962**만 남습니다. 사용자 화면의 문장은 일반적으로 토큰별 확률을 표시하지 않기 때문에 두 문장은 동등하게 확신에 차 보일 수 있습니다.

**중요:** logprob 자체도 신뢰할 만한 '정답 확률'을 보장하지 않습니다. 낮은 토큰 확률은 점검 신호가 될 수 있지만 높은 확률도 환각을 배제하는 증거는 아닙니다.

## 14. 완화책 1 — 사실을 입력에 제공한다(RAG·원문 첨부)

검색, DB 조회, API 또는 사용자가 제공한 문서에서 검증 가능한 사실을 가져와 질문과 함께 넣습니다.

1. 먼저 필요한 근거를 검색합니다.
2. 질의와 관련된 부분을 골라 모델에 제공합니다.
3. 모델이 **제공된 근거에 의존**해 답하게 합니다.
4. 근거에서 확인할 수 없는 주장은 보류하게 합니다.

원문은 이를 **평평한 추측을 더 집중된 추측으로 바꾸는 방법**으로 설명합니다. 다만 근거가 오래되었거나 검색 결과가 틀리거나 모델이 문서를 잘못 읽으면 오류는 남습니다.

## 15. 완화책 2 — `모르겠습니다`를 적절한 답으로 학습시킨다

근거가 부족할 때 보류(abstention) 또는 불확실성을 정확히 표시하는 출력을 장려합니다. 원문은 모델 학습·평가에서 틀린 단정보다 정직한 보류에 더 적절한 점수를 주어야 한다고 설명합니다.

1차 연구인 **Kalai et al. (2025), Why Language Models Hallucinate** 역시 평가가 추측을 보상하면 보류보다 틀린 답을 택하는 유인이 생길 수 있다고 분석합니다. 이는 이 문서의 추가 1차 자료이며 Outcome School 원문과는 별개입니다.

## 16. 완화책 3 — 확률과 답변 불일치를 진단 신호로 사용한다

토큰 logprob가 제공되는 시스템에서는 연도·고유명사 등의 낮은 확률 후보를 검토 대상으로 표시할 수 있습니다. 같은 질문을 여러 번 수행했을 때 **사실 토큰이 서로 달라지는 현상**도 원문의 대표적 경고 신호입니다.

- 토큰 확률은 **진단 신호**이지 자동 사실 검증기가 아닙니다.
- 여러 답이 **같아도** 공동의 착각일 수 있습니다.
- 불일치와 근거 부족이 발견되면 실제 출처를 조회해야 합니다.

## 17. 완화책 4 — 근거와 계산을 먼저 확보한 뒤 답한다

원문의 소수 예제에서는 바로 `Yes` 또는 `No`부터 생성하지 말고, `3,827`의 인수분해를 확인한 다음 최종 판단하도록 합니다.

```text
질문: 3,827은 소수인가?
검증: 43 × 89 = 3,827
결론: 아니요. 합성수입니다.
```

내부 추론만 늘리는 것으로 참이 보장되지는 않습니다. 산술의 경우 계산기·코드 실행처럼 **검증 가능한 도구**를 사용하는 것이 더 강한 방안입니다.

## 18. 완화책 5 — 사실 응답에는 낮은 Temperature를 고려한다

낮은 Temperature는 무작위 선택을 줄여 출력 변동성을 완화하지만 앞서 본 **최상위 잘못된 후보** 문제는 해결하지 못합니다. 따라서 Temperature를 낮추는 것만으로 환각 감소를 보장하지 말고 **검색·검증·보류 정책**과 함께 사용해야 합니다.

## 19. 완화책 6 — 사실을 가진 부분을 우선 검증한다

이름, 연도, 숫자, 금액, 사건, 논문 제목, URL·DOI, 의료·법률 주장과 같은 **검증 가능한 사실 주장**을 집중적으로 검사합니다.

- 출력에서 핵심 주장을 개별 단위로 분리합니다.
- 그 주장마다 신뢰할 만한 원문 또는 도구 결과와 대조합니다.
- 불일치하거나 근거가 없으면 수정 또는 보류합니다.
- 문장 유창성과 근거 검증을 서로 다른 단계로 관리합니다.

원문은 어떠한 하나의 완화책도 환각을 **완전히 없애지는 못한다**는 점을 강조합니다.

## 20. 여섯 원인과 대응책 연결

| 환각이 생기는 단계(원문 분류) | 우선 고려할 대응 |
| --- | --- |
| 1. 아는 근거 없이도 토큰을 채우려 함 | 불확실할 때 보류를 장려하는 학습·평가 |
| 2. 평평한 분포에서 임의의 토큰을 선택함 | 낮은 temperature + 외부 근거 |
| 3. 잘못 출력한 첫 토큰을 뒤로 수정하지 못함 | 먼저 계산·근거 확인, 필요 시 재검증 |
| 4. 잘못된 첫 판단이 후속 문장을 지배함 | 단계 분리, 도구 검증, 사후 사실 확인 |
| 5. 그럴듯한 조합이 가짜 참고문헌이 됨 | DOI·서지·공식 출처 조회 |
| 6. 최종 문장이 확률 정보를 숨김 | logprob/반복 생성 진단 + 근거 검증 |

## 21. 실무에 적용할 때 구별할 것

| 잘못된 판단 | 더 정확한 판단 |
| --- | --- |
| 문장이 유창하면 사실일 것이다 | 유창성은 사실성을 입증하지 않습니다. |
| 같은 답을 여러 번 말하면 사실이다 | 동일한 추측이 반복될 수 있습니다. |
| 첫 토큰 확률이 높으면 근거가 충분하다 | 높은 확률은 사실의 외부 검증이 아닙니다. |
| RAG를 사용하면 자동으로 환각이 사라진다 | 검색 품질·근거 선택·인용 검증이 필요합니다. |
| 모델은 `모르겠다`고 말할 수 없다 | 보류 표현을 출력하게 하는 학습·프롬프트·정책이 가능합니다. |

### 실습 점검

1. 원문 예시의 **95%와 14%**가 각각 어떤 상황인지 설명해 봅니다.
2. 확률이 14%인 후보를 temperature 0으로 고정하면 무엇이 **좋아지고 무엇이 그대로인지** 구별합니다.
3. `3,827 = 43 × 89`를 실제 계산으로 확인하고, 생성된 주장과 도구 결과를 분리합니다.
4. 가짜 논문 인용이 만들어지는 메커니즘과 검증 절차를 설명합니다.
5. RAG 시스템에서 **근거 검색 성공 / 최종 답변 사실 확인 성공**을 따로 평가합니다.
